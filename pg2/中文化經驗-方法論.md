# 《裝甲元帥2》中文化經驗萃取:閉源 DirectDraw 老遊戲 CJK 中文化方法論

本文把 [中文化規劃.md](中文化規劃.md) §7(2026-07-17–18 的實作階段 RE 攻堅)萃取成可重用方法論,供**日後對其他閉源 DirectDraw 老遊戲做 CJK 中文化**參考。PG2(《裝甲元帥2》,SSI 1997)是本 repo 第一個**非 5D Pascal 引擎**的中文化對象(全新 VC++/DirectDraw),PG1/AG/PacGen 累積的經驗有多少能搬、哪裡不能搬,本輪都踩過一次。

標註慣例:**[已證]** = PG2 一役實作/實機驗證過;**[推定]** = 由已證機制外推、下一款遊戲動手前需再驗;**[通用]** = 已在 PG2 與至少一款前作(PG1/AG/PacGen)重複出現,判斷為跨遊戲通則。

---

## 1. 引擎判定與策略

### 1.1 別假設「同系列 = 同引擎」——先查 import table + build path 字串 [已證]

PG1《裝甲元帥》、AG《盟軍元帥》是 Borland Pascal + WinG(256 色 DIB blit);PacGen《太平洋元帥》是 DirectDraw + 自訂 8×8 點陣字;PG2 表面上是「系列第四款」,但反組譯一開就發現它是**全新 Visual C++ 引擎**——`PANZER2.EXE` import `MSVCRT.DLL`,反組譯內含建置路徑字串 `C:\pz97\main\Src\Scenario.c`(專案代號 `pz97`)。

**可重用的判定法**(成本低、開工前先做):
1. **import table**:有 `MSVCRT*` 通常是 VC++;有 `WinG*` 是 Borland/WinG 世代;純 `DDRAW.dll` 無 GDI 文字 API(`TextOutA` 等)代表繪字管線走自訂點陣字(見 §1.2)。
2. **反組譯字串表**:老遊戲常把編譯機的絕對路徑(`C:\...\Src\*.c`)、內部工具訊息、debug 字串留在 `.rdata`,是判斷專案代號 / 開發年代 / 模組劃分的免費證據。
3. **結論**:PG2 與 PG1/AG 的 5D 引擎**不同源**,本 repo 既有的反組譯位址與 SCENARIO.TDB 機制**不適用**;但這不代表「全部重來」——見 1.2,渲染管線的**格式**與工具鏈仍可能同族。

### 1.2 引擎不同源 ≠ 渲染管線不同族 [已證]

PG2 判定完引擎後的關鍵發現:雖然整個引擎重寫了,**畫面內文字用的自訂點陣字格式與 PacGen 的 `TFONT` 完全同族**(header 16 bytes、256×4 offset table、`[width][8×8 px]` glyph、前景 0x00/背景 0xff)。這代表 PacGen route C(見 §1.3)的**工具鏈**(`build_atlas.py`/`font_rebuild.py`/`build_hooked_exe.py`)可以大量複用,只是**位址要對這款 EXE 重新定位**——方法可靠、結論要現做(這是 `retro-directdraw-hires-cjk` skill 的核心紀律)。

**可重用的判斷順序**:先確認「引擎工具鏈世代」(§1.1),再獨立確認「文字渲染管線格式」(font header 逐 byte 核對),兩者可能不一致——別因為引擎變了就假設連字型格式也全變,也別因為字型格式眼熟就假設整個引擎能沿用舊位址。

**PG2 的雙管線**(老 Windows 遊戲常見模式,值得作為通則記錄):
- **管線 A:GDI 對話框**(視窗層,選項/存讀檔/連線/錯誤框)——用 `DialogBoxParamA`+ EXE `.rsrc` DIALOG template,字型走系統 API(`CreateFontA`),**中文化只需換 facename + charset**,不必碰渲染邏輯。
- **管線 B:遊戲主畫面**(DirectDraw surface 層,地圖標籤/選單/標題)——不走 GDI,自訂點陣字 blit,**是主要工程量**,需 route C。
- 兩條管線各自獨立、各自要處理;判斷哪段文字走哪條管線,看它是「Windows 對話框」還是「遊戲主畫面內」,對應 import table 裡的 API 呼叫點是 GDI 還是純 DirectDraw。

### 1.3 語言槽注入 vs 新增語言分支 [已證]

多數 1990s 歐美遊戲(尤其 SSI 系列)為了發行歐洲多語版,原生就有 3–4 個語言分支(英/法/德/西)。**中文化不必新增語言分支**,寄生一個現成語言槽成本遠低於從零接一條新分支:改該語言槽對應的字型檔(換成 CJK atlas)+ 把該語言設為預設,即可。

**PG2 的路線選擇教訓(值得記錄的反轉)**:
- 一開始的方案是「寄生法語/德語槽」——理由是這兩槽用簡單的 8×8 TFONT(與英文主字型的複雜格式不同),可直接套用 PacGen 現成工具鏈,工程最小。
- 動手 PoC 後發現法語槽有**兩個獨立問題**:①LOGO 等語言後綴素材缺(黑屏,非崩潰)②**法語字型在該遊戲副本裡未被正確載入 → 全域字型指標野指標 → 首次繪字即崩**。
- **轉向英文(預設)槽**:直接把中文注入英文資料檔,不必動語言選擇 byte、不必面對法語字型載入問題,同樣達成「開機就是中文」的使用者需求,且**更簡單**(少一個語言 patch)。
- **可重用的判斷法**:「理論上最省工具鏈」的語言槽,不一定是「實際最省風險」的語言槽——**預設/主要語言槽通常經過最多測試、載入路徑最穩**,寄生非預設語言槽前,先用最小 PoC 驗證該槽本身在你的目標平台(wine/現代 Windows)上能正常初始化,別假設「档案存在 = 能載入」。

### 1.4 自建 2-byte CJK 引擎(沿用 route C)[已證,方法沿用自 PacGen]

8×8(或更小)點陣字**物理上塞不下可讀中文**,這是第一性事實,不需要每款遊戲重新論證。`retro-directdraw-hires-cjk` skill 已把手法定名為三條路徑(A/B/C),PG2 與 PacGen 一樣選 **route C(不動畫布,只拉高 font 字高 + 2-byte hook)**,是三條裡工程量最小的:

1. 確認字高是 **memory-read**(如 `[font+8]`)而非 immediate——改 font header 即可讓渲染迴圈畫更高,EXE 邏輯不用動。
2. CJK atlas 做成**與原生 drawGlyph 相容的 mini-TFONT**,讓 hook 直接呼叫原 drawGlyph、復用原 blit 邏輯。
3. 自訂 **dense 2-byte 私有編碼**(非裸 Big5):`dense=(lead-LEAD0)*W+(trail-TRAIL0)`,兩 byte 皆 ≥0x80、hook 純算術無查表,塞得進小 code cave;資料檔字串由 glossary 重產,重編碼零成本。
4. 無 code cave 就追加 PE 節(PG2 用 `.cjk`,同 PacGen 命名慣例);固定 base(non-ASLR)的老 EXE,絕對立即數免 reloc。
5. **多繪字路徑各自 hook**——這條在 PG2 被完整驗證:主選單/清單走 `drawStringCore`,簡報/word-wrap 走另一個含斷行邏輯的模組(`0x43e955`),兩條各需獨立 hook,且 word-wrap 那條因為多了斷行/量測/兩段 render,是**唯一需要專屬 hook 的路徑**,實作難度明顯高於單行繪字。

## 2. 核心教訓:第一性原理勝過打地鼠

這是本輪中文化過程最重要的方法論收穫。PG2 在字型引擎完成後,陸續冒出「劇本清單標題被截斷」「戰役選單也截斷」「狀態列顯示 `(null)`」「採購畫面單位名空白」「提示文字飛出螢幕外」等一串看似不相關的症狀。**逐條 hook 症狀路徑是打地鼠**——按下去一個、換個畫面又冒一個,永遠修不完;真正有效的做法是**停下來找共同機制**。

### 2.1 案例一:截斷/空白/(null) 一族的共同根源 = `_pctype` ctype 表 [已證]

**打地鼠階段**:劇本清單標題截斷,先假設是「量測寬度算過量、字被裁掉」,做了 2-byte 感知的量測 hook——**零效果**(baseline 與 fixed 版逐像素相同)。再仔細比對才發現截斷與寬度無關,是**特定 byte 值**觸發(24 個 ASCII 字不截斷、2 個 CJK 字卻截斷);往下追,定位到清單標題來源函式內一段逐 byte 分類迴圈,用 CRT ctype 巨集(`& 0x157`)判斷字元類別。第一輪修法是在該函式 patch;隨後發現同款 ctype 分類邏輯在 EXE 內**至少有 5 個 byte 級相同的姊妹函式**(劇本清單一個、戰役選單另一個、其餘畫面各自的),於是把 5 個全找出來逐一 patch。

**第一性原理階段**:5 個 patch 做完後,狀態列 `(null)`、採購畫面空白依然存在——因為 EXE 裡這類 mask-`0x157` 的同族 classifier 其實有 **約 10 個**,劇本/戰役清單只是先撞到的 5 個。回頭拆到底層機制:所有這些 classifier 都呼叫 CRT 的 `_pctype` 全域 ctype 表,用 **`movsx`(符號延伸)**讀取字元 byte——中文的高位元組(0x80–0xFF)被符號延伸成負數,變成**負索引**,讀到表格前面的 shadow 區,回傳 class 0(非可列印),於是被引擎當成字串終止符或不可顯字元處理。**這是一個共用的 CRT 表,不是各畫面各自的邏輯**。

**修法(單點,取代 5 個/更多 per-site patch)**:不能直接把 `_pctype` 的負 shadow 區填值——那塊記憶體是**活的字串資料**(其他錯誤訊息字串等),砸了會壞掉別的功能(Chesterton fence,見 §3.4)。改成**指標 repoint**:另建一張新表(負索引區填「可列印」的類別值、正索引區逐 byte 複製原表 0x00–0xFF),把 `_pctype` 指標改指向新表的正 0 位置。ASCII 行為**逐 byte 相同**(blast radius 最小),但高位元組不再被誤判——同一個 patch 同時修好劇本清單、戰役選單、狀態列、採購,是先前 5 個 per-site patch 的**嚴格超集**。

**教訓**:當「同一類症狀」在多個畫面各自冒出時,**先問「這些呼叫的是不是同一張表/同一個函式」,再決定要不要動手 patch**。逐一 hook 症狀路徑不是錯,但要當作臨時止血,做完第二、第三個相似 patch 時就該停下來找根源。

### 2.2 案例二:提示位置/單位名錯位的共同根源 = 次要路徑寬度量測不 2-byte 感知 [已證]

`_pctype` 根治後,又冒出三個新症狀:主選單提示文字飛出螢幕外、戰場滑鼠懸停單位名在狀態列消失、採購畫面單位名「看起來很擠」。前兩個一開始被當成三個獨立畫面問題看待,若照 §2.1 之前的打地鼠習慣,會變成三個各畫面的專屬 patch。

**根源**:量測寬度用的 clamp stub(先前為了修 §3.3 的 crash 而加的一個「把字元 clamp 成 byte」的小 patch)只解決了「不當機」,沒有解決「量測正確」——它仍把 CJK 的每個 byte 當成一個獨立字元去查表加總寬度,於是**一個中文字(2 byte)被量成 2 個字寬**,凡是用量測結果去算座標的地方(置中 `x=錨點−寬/2`、右對齊 `x=錨點−寬`)全部高估、全部錯位。這條量測邏輯被 28+ 個呼叫點共用(提示定位、狀態列置中、採購對齊……)。

**修法(單點,25 bytes)**:把這個 clamp stub 改成 2-byte 感知——用「量測迴圈固定讀到負值(高位元組被符號延伸)」與「atlas 繪字前進固定讀到正值」這個既有的正負號差異當判別依據:負值(量測中的 CJK 高位元組)回傳半寬(一個 CJK 字兩個 byte 各算半寬,兩者相加剛好等於實際前進寬度);正值維持原邏輯。**一次修好全部量測呼叫點**,不必逐畫面加專屬 hook。

**教訓**:同一族症狀(這裡是「位置算錯」)即使表面分散在不同 UI 元件(提示框、狀態列、清單對齊),常見根源是**某個被廣泛共用的底層函式**(這裡是寬度量測)。判斷法:先看崩潰/錯位的呼叫點是不是收斂到少數幾個函式,而不是先入為主假設每個畫面各自獨立。

### 2.3 判斷法總結(可直接套用到下一款遊戲)

遇到「同類症狀在多處出現」時,依序自問:

1. **這些呼叫點背後,是不是共用同一個函式 / 同一張表 / 同一段被複製貼上的邏輯?**——老引擎的 UI 代碼常有「同一段邏輯被複製到多個畫面」的情況(PG2 的 5–10 個 ctype classifier 姊妹函式就是這樣),乍看要逐處修,其實有更上游的共用點。
2. **先做最小 PoC 驗證假設,別急著擴大修補範圍。**PG2 案例中先假設「寬度過量」做了一次 2-byte 感知量測 hook,結果零效果——**這次「失敗的 PoC」本身就是有效資訊**,它排除了一個假設,逼出下一步去找真因,而不是繼續在錯誤方向上加碼。
3. **對照組要控制變因。**判斷某個異常是不是自己引入的,要同關卡、同 hex 位置比較英文版與中文版,不能用「可能是載入到不同關卡」這類未經控制變因驗證的說法帶過。
4. **改動前先確認會不會傷到其他活資料(Chesterton fence)。**共用表格/共用函式常常同時被別的邏輯使用,直接覆寫前先確認那塊記憶體/那個呼叫路徑還有誰在用(見 §3.4)。
5. 找到共同根源後的修法優先序:**指標 repoint / clamp 邏輯調整**(不動資料本身、行為變化侷限)優於**逐點 patch**(改動面廣、日後新增畫面還要再補)。

## 3. 踩雷清單

### 3.1 `sprintf(buf, name, …)` 把名稱當 format 字串,NULL name 觸發崩潰 [已證,原版引擎既有 bug]

實機玩到戰場、右鍵看單位資訊時觸發 `page fault read 0x0`。追根源後發現這是**原版引擎既有的設計缺陷,不是中文化引入的**:PG2 UI 有個常見寫法是 `sprintf(buf, name, ...)`——把「查表查到的名稱字串」直接當 `sprintf` 的 **format 字串**用(而非資料參數)。對某些 hex 值,查表(一張約 400+ 筆的字串表)間歇性回傳 NULL(疑似未初始化或殘留指標),未加防護的繪字路徑呼叫這個 `sprintf`,底層 `_output` 函式對 NULL format 字串解參照 → 崩潰。

**判斷「是我方引入還是原版既有」的方法**(可重用):
- 崩潰路徑上的每一段程式碼是不是都是原版未改的邏輯,我方 patch 是否完全沒觸及。
- 引擎自己是否已經對這類問題有防禦意識的痕跡(PG2 裡有一條 `null string at %d,%d` 的 debug 字串,以及**只有一個**繪字變體加了 NULL 防護、其餘同類變體沒加)——這種「加了一半的防禦」通常是原開發團隊自己也踩過、修了一部分沒修完,是原版既有 bug 的強證據。
- 英文原版在同樣的 hex/資料組合下,理論上也會踩到同一顆雷(即使沒人踩過);中文化只是**用了更多樣的資料/操作路徑**,把潛伏的 bug 撞出來。

**修法**:不改上游邏輯,直接 hook 底層 `_output` 函式入口,format 參數為 NULL 就直接回傳(相當於印出空字串),讓標籤顯示空白而非崩潰——修法侷限在崩潰發生的最後一道防線,非 NULL 路徑零行為改變。

### 3.2 atlas 前景/背景顛倒 = 白底 / 中文消失 bug [通用,PacGen 已踩過同一顆雷]

自建 CJK atlas 時,若前景(筆畫)/背景像素值與原生字型的慣例(PG2/PacGen 皆為前景 `0x00`、背景 `0xff`,經 `xlat` 調色透明表映射)不一致,會出現「文字變白底方塊」或「文字整個消失變透明」。**這是 PacGen 中文化已經踩過的雷**(見 `pacgen/docs/11-2byte-engine.md`),PG2 動手做 atlas 時已知道要對齊像素慣例,一次做對,沒有重複踩雷。

**可重用的檢查法**:動手做 atlas 前,**先靜態讀原生字型檔的一個已知 glyph**(如數字 `1`),逐 pixel 印出來確認前景/背景是哪個值,再用同慣例做 atlas。字型的字高補列(把 8px 字型的資料補到 16px)時,補的空白列也要用「背景值」而非「前景值」,否則會在字元上方多出一條實色色塊(PacGen 案例:`font_rebuild.py` 補列用了 `0x00` 而非 `0xff`,導致每個空格字元變成上半實心色塊)。

### 3.3 `movsx` vs `movzx` 讀字元的差異,決定高位元組是正是負 [已證]

同一份 EXE 裡,不同的「讀一個字元 byte」的組合語言指令,行為可能不同:`movzx`(零延伸)讀高位元組(0x80–0xFF)得到正值(0x80–0xFF);`movsx`(符號延伸)讀同樣的 byte 會得到**負值**(-128 到 -1)。PG2 至少有兩個獨立位置踩到 `movsx` 的坑:①`glyphWidth` 量測函式用 `movsx` 讀字元 → 高位元組變負索引 → 查表越界崩潰;②CRT ctype classifier 家族(§2.1)同樣用 `movsx` → 負索引讀到 shadow 區。

**可重用的檢查法**:每個「讀字元 byte 再拿去查表/判斷」的函式,反組譯時要**個別確認**用的是 `movsx` 還是 `movzx`——不能因為兩個函式表面邏輯像(都是「讀一個字元」),就假設指令選擇一樣。凡是要支援高位元組(2-byte CJK 的 lead/trail)通過的路徑,只要沿路有一處 `movsx`,就是潛在崩潰/誤判點。

### 3.4 Chesterton fence:共用表格砸不得,改用指標 repoint [已證,方法論]

`_pctype` 的負 shadow 區(表格前方)不是「未使用的死空間」,而是**活的字串資料**(其他錯誤訊息字串、版本字串等剛好落在那塊記憶體)。直接把負 shadow 填值會砸掉這些字串,產生新的、更難追的 bug。這正是「柵欄原則」的具體案例:**先確認一塊看似可覆寫的記憶體背後有沒有別的用途,再決定怎麼改**;PG2 的解法是不動原表,另建新表 + 改指標,是「不确定會不會傷到別人就別動原資料」的保守解。

### 3.5 清背景框 / 固定文字框是照原生字高設計的 → 拉高字高後 CJK 殘影或溢出 [已證]

route C 把字高從 8px 拉到 14/16px 後,狀態列 / 清單這類「重畫前先清舊字」的欄位會出現**換字串殘影**(切到較短或空字串時,舊字的下半截留在畫面上)。根因不是繪字、也不是字級本身,而是**清舊字的背景 Blt 用一張 descriptor 表的固定 RECT,那些 RECT 的高度是照原生 8px 字算的(PG2 實測約 7px)**;CJK 頂端對齊、字身佔 `top..top+H−1`,清框只清到 `top+6`,下緣 `H−7` px 沒被清掉 = 殘影。**縮字不能自然解**(任何可讀 CJK ≥12px 都比 7px 清框高,PG2 實測 12px 仍殘 ~4px)——這又是一個「表面像字級問題、實際是固定幾何問題」的例子,呼應 §2:別被「換個參數應該就好」的直覺帶著走,先找真機制。**修法**:把該表相關欄位的 `bottom` 抬高成 `top+字高+1`(純資料 patch,不動 code)。注意這把 Blt 來源往下多讀幾列,要**實機確認多讀到的來源列是乾淨底紋**(共用單一 bar 底紋條時成立),否則會 Blt 到垃圾。

**同族雷(固定框高)**:固定像素高的**文字框 / 彈出 popup**(對話、地圖上的提示 / 顧問簡報)也是照原生 8px 字設計的固定值,CJK 換行需要更多行時會**溢出框外**、且這類 popup 常**無捲動**。這是**另一個 caller 的框幾何**問題,與繪字 hook / word-wrap hook 無關;縮字只能緩解(塞更多行)、無法根治,根治要改框高或加捲動。判斷法同上:先確認「畫超出去的是誰設的框」,別誤以為是 word-wrap 邏輯壞掉。

### 3.6 多臉 `.ttc` 字型未指定 face index → 預設臉可能是錯的語言 [已證]

用 PIL / `ImageFont.truetype` 從 `NotoSansCJK-*.ttc` 這種**多語言合集字型**烤 atlas 時,若不指定 `index`,預設拿 **face 0**——而 Noto CJK 的 face 0 是**日文**(枚舉:0=JP / 1=KR / 2=SC / 3=TC / 4=HK)。對純漢字**幾乎無差**(同一套 glyph),但**標點置放慣例不同**(句號 / 頓號 / 間隔號:日式置左上「kuten」、中式置左下),做繁中化若拿到日文臉,這幾個標點會位置錯。PG2 案例:16px 出貨版與 14px 版都曾誤用日文臉,逐字比對 1,582 字僅 3 個標點有像素差,改用 `font_index=3`(繁中臉)。**檢查法**:烤 atlas 前用 `fontTools.ttLib.TTCollection` 枚舉 `.ttc` 各 face 的語言、**顯式選繁中臉**;做完逐字比對兩臉差異(通常只有幾個標點)。低風險但真實的在地化保真度 bug,容易因「漢字看起來都對」而漏掉。

### 3.7 atlas 收字判斷用「CJK 碼段白名單」會漏字 → 用 `>=0x80` 全收 [已證]

決定「哪些字要進 atlas / 要 2-byte 編碼」時,若用 CJK 碼段白名單(`0x4E00–0x9FFF` 等)判斷,會**漏掉夾在譯文裡的非 CJK 高位字元**——最典型是音譯人名 / 地名用的 **U+00B7 間隔號(‧ / ·)**,它落在 Latin-1 區、不在 CJK 段,一漏就在編碼某個含它的檔案時炸掉(找不到 glyph;PG2 是 `MALTA.TXT`)。**修法**:凡 `ord(c) >= 0x80`(ASCII 以外)全收進 atlas 給 2-byte glyph,`< 0x80` 維持單 byte ASCII。這樣任何實際出現在譯文母檔裡的字都有 glyph,不必逐一維護碼段白名單。

## 4. 驗證教訓

### 4.1 Headless 靜態驗證會漏掉互動玩家路徑 [已證]

Wine + Xvfb 的 headless 截圖驗證能可靠涵蓋「畫面渲染對不對」(主選單、清單、簡報文字),但**漏掉了兩類 bug**,都是使用者實機玩到才回報:
- 右鍵看單位資訊的 popup(§3.1 的 `sprintf` NULL 崩潰)——headless 自動導航很難穩定觸發這個互動。
- 進入採購/升級畫面(某些畫面沒有可靠的自動導航路徑能截到)。

**教訓**:出貨前除了 headless 截圖驗證(涵蓋率高、可重複、適合每次改動後回歸測試),**還要規劃一輪走「正常玩家路徑」的實機測試**(開一場戰役、玩幾回合、點開會被使用者點開的選單/面板),尤其是涉及右鍵選單、彈出視窗、需要遊戲內狀態(存檔進度)才能到達的畫面。這與 `verification-fidelity` skill 的核心提醒一致:**驗證若用了比較寬鬆的替身(這裡是「headless 能截到的路徑」)而非真正會出狀況的互動路徑,等於沒驗**。

### 4.2 對照組要控制變因 [已證]

判斷某個顯示異常(如狀態列 `(null)`)是不是中文化引入的,要**同一關卡、同一 hex 位置**比較英文版 vs 中文版的行為,不能用「可能是載入到不同關卡」這類未經控制變因驗證的推測帶過。PG2 案例中用「同一場戰役同一回合(如某場戰役 Turn 1)」三方比較(英文原版 / 中文+舊 patch / 中文+新 patch),才確認 `(null)` 是我方尚未修到的 ctype classifier 造成、且新 patch 確實修好——三方對照缺一,結論就站不住。

## 5. 打包 / AppImage 生命週期雷(跨遊戲通用,重要)

以下兩類雷是在 PG2 打包後、使用者實機回報「換了新版 AppImage 但舊 bug 還在」時才發現的,**根因與中文化渲染引擎本身無關,是 AppImage 啟動腳本(AppRun)的生命週期設計問題**。判斷這兩類雷**很可能也存在於本 repo 既有的 PG/AG/PacGen AppImage**(因為 AppRun 骨架同源),日後重打包這幾款時應一併檢查。

### 5.1 AppRun 只在首次啟動同步遊戲檔,之後永不更新 [已證,PG2 踩到;推定同源於 PG/AG/PacGen]

**症狀**:使用者下載新版 AppImage、覆蓋安裝、啟動,回報「當機修了還在」「採購空白還在」——但這些 bug 明明已經在新版 EXE 修好了。追查後發現 AppRun 的邏輯是「檢查 `~/.local/share/<game>/` 是否已存在遊戲檔,不存在才 `cp` 一份過去」——**只在第一次啟動時同步**,之後即使 AppImage 內容換了(新 EXE、新資料檔),本機那份已安裝的舊檔案永遠不會被覆蓋。使用者以為自己在跑新版,實際上跑的還是第一次安裝時的舊 EXE。

**修法**:在遊戲檔目錄旁放一個內容雜湊(對關鍵檔案算 hash)當版本戳(`VERSION`);AppRun 每次啟動都比對這個戳,不一致就**重新同步遊戲檔**,同時**保留使用者的存檔目錄**(`SAVE/`、`USERSCEN/` 等)不被覆蓋清空。沒有 `VERSION` 戳的舊安裝(使用者用舊版 AppImage 裝的)視為「需要更新」,自動補上這道機制。

**可重用的檢查法**:任何用「首次 cp 到本機再執行」模式的 AppImage/portable 包裝,都要問「更新這個 AppImage 後,已經跑過一次的使用者機器上,舊檔案什麼時候會被換掉?」——如果答案是「不會,除非手動清掉本機目錄」,這就是同一顆雷。

### 5.2 殘留 wineserver 未清,第二次啟動接舊 server 導致 X window 失效崩潰 [已證,推定同源於 PG/AG/PacGen]

**症狀**:同一個遊戲第二次啟動(第一次跑完關掉、或崩潰後重開)有機率直接 `BadWindow (X_CreateWindow)` 崩潰。根因是**上一次執行遺留的 wineserver 沒被清掉**,新的啟動流程接上這個殘留 server,而該 server 握著的 X window ID 已經隨上一次的 X client 生命週期結束而失效,新 client 拿著失效 ID 操作 → X protocol 錯誤直接崩潰。

**修法**:每次啟動遊戲前,先對**這個遊戲專屬的** wine prefix 執行 `wineserver -k`(kill),並輪詢等待進程真正結束(避免 kill 訊號送出但進程還沒死就接著啟動,產生 race),再啟動遊戲本體。**範圍要收斂在只清這個遊戲自己的 wineserver**,不要誤傷同機其他遊戲(AG/PacGen 各自獨立的 WINEPREFIX)或使用者自己開的其他 wine 應用(不同 `:N` display)。

**可重用的檢查法**:凡是「AppImage 每次啟動都重新拉起一個背景 daemon(wineserver 或類似角色)」的架構,都要確認舊 daemon 的生命週期有沒有被妥善收斂——沒有清乾淨的背景進程是這類間歇性崩潰的典型根因,且**只在第二次之後的啟動才會發生**,容易被第一次啟動的順利驗證蓋過去,是驗證時的死角。

### 5.3 內建整數放大 + fallback [推定,polish 層級]

PG2 原生解析度 640×480,在現代高解析度螢幕上顯示過小;wine 虛擬桌面本身不會拉伸內容(只是在桌面左上角畫一塊 640×480、其餘補黑)。解法是**內建 gamescope 做整數 nearest 放大**(2×/3×),透過環境變數(如 `PG2_SCALE=2x`)opt-in,且**gamescope 啟動失敗時要能自動退回 1×**,不能讓「放大失敗」變成「遊戲整個起不來」。這屬於錦上添花的 polish,不影響中文化本身,但打包時建議把 fallback 路徑當作**必測項**(headless 環境常常沒有真正的 GPU/DRI3,是驗證 fallback 是否生效的天然測試場景)。

## 6. 分工 / 流程經驗

### 6.1 依任務性質選模型 [通用]

RE 攻堅(判斷共同根源、決定 patch 策略、字渲染機制樞紐判斷)用高階推理模型;機械性工作(解壓、跑既有 script、列 PE 資源、批次改檔、打包)可降級到較便宜的模型,一律繼承主 session 的高階模型是不必要的成本。判斷準則:這一步驟需要的是「理解與判斷」還是「照既定流程執行」,前者留給高階模型,後者可以外包。

### 6.2 每完成一輪就 commit + push [通用]

每個階段(規劃 → RE → 翻譯 → 字型引擎 → EXE patch → 打包)產出並自我審過後就進版控,不要累積一大包改動才一次 commit。好處是每個階段的成果都有獨立的還原點,出問題時可以精確定位是哪一輪引入的。二進位大檔(AppImage/zip/DAT)不進 git,只記錄 md5/路徑清單(見 `pacgen/docs/knowledge-base/dist-manifest.md` 的作法)。

### 6.3 背景 subagent 不要設了背景監看就結束 [通用]

派長時間跑的背景 subagent(如跑一輪完整 wine 實機驗證、跑打包腳本)時,要確保有人在收工前確認它真的跑完並檢查結果,不能派出去就當作任務完成——背景進程結束的通知要被消化,不是「派了就算數」。

## 7. 一句話總結 / 下一款遊戲的檢查清單

PG2 證明了「引擎換了,方法論不必跟著全部重來」——**judge 引擎世代(import table + 建置路徑字串)→ 獨立 judge 渲染管線格式(font header 逐 byte)→ 能複用的複用(PacGen route C 工具鏈),不能複用的重新定位(位址)**。真正的高風險不是「找不到字型格式」,而是**同類症狀反覆出現時,有沒有及時從「逐點 patch」切到「找共同根源」**;以及**headless 驗證覆蓋不到的互動玩家路徑**與**AppImage 生命週期(更新/殘留進程)**這兩塊,同樣容易被誤判成「已經修好」而實際上使用者機器上還在跑舊 bug。

下一款閉源 DirectDraw 老遊戲動手前,建議依序打勾:

1. import table + 建置字串判引擎世代;font header 逐 byte 判渲染管線是否與既有成果(PacGen/PG2)同族。
2. 語言槽選預設(英文)優先於「理論上工具鏈好複用」的非預設槽,除非已 PoC 驗證非預設槽能穩定初始化。
3. 字高 memory-read 確認後走 route C;多個繪字路徑(單行 vs word-wrap)各自 hook。
4. 遇到同類症狀在 ≥2 處出現,先找共同函式/共同表,別急著加第 3 個 per-site patch。
5. 動 CRT 共用表(ctype/locale 之類)前,先確認會不會砸到旁邊的活資料,能 repoint 就不要覆寫原表。
6. 检查全部「讀字元查表」的位置 `movsx`/`movzx` 是否一致,高位元組會不會變負索引。
7. 出貨前排一輪正常玩家路徑實機測試,不只靠 headless 截圖。
8. AppImage 打包前檢查:更新後舊安裝會不會同步新檔?每次啟動前有沒有清乾淨上一輪的背景進程?
