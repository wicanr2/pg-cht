# 《裝甲元帥2》(Panzer General II, SSI 1997)繁體中文化規劃

本文件盤點 PG2 的檔案結構、文字渲染機制與可跑性,並提出繁中化 + 跨平台(Linux AppImage / 現代 Windows)的技術方案。

**標註慣例**:**[已實測]** = 本輪在乾淨環境反組譯 / 解析 / 實機驗證過;**[推定]** = 由已測機制外推、動手前需再驗;**[未探索]** = 尚無資料。所有反組譯位址以 `PANZER2.EXE` ImageBase `0x400000` 為準。

素材:`PG2_v2.5.7z` → `Panzer2/`(本輪解壓於 scratchpad,未進 repo)。

---

## 1. 遊戲概況

- **《裝甲元帥2》(Panzer General II)**,SSI / Mindscape 1997,回合制六角格戰棋,PG 系列(SSI「5D」家族)的次世代作品。
- **與 PG1 / AG / PacGen 的引擎差異(關鍵)[已實測]**:
  - PG1《裝甲元帥》、AG《盟軍元帥》是 **Borland Pascal + WinG**(256 色 DIB blit),PacGen《太平洋元帥》是 **DirectDraw + 自訂 8×8 點陣字**。
  - **PG2 是全新的 Visual C++ 引擎**:`PANZER2.EXE` import `MSVCRT.DLL`,反組譯內含建置路徑 `C:\pz97\main\Src\Scenario.c`(專案代號 pz97 = Panzer 1997)。繪圖走 **DirectDraw**(import `DDRAW.dll`),音效走 Miles(`mss32.dll`),過場影片走 Smacker(`smackw32.dll`),連線走 DirectPlay(`dplayx.dll`)+ ClubSSI(`clubdll.dll` / `gamechat.dll`)。
  - 因此 **PG2 與 PG1/AG 的 5D 引擎不同源**,本 repo 既有的 AG/PG 反組譯位址與 SCENARIO.TDB 機制**不適用**;反而 PG2 的**自訂點陣字引擎與 PacGen 同族**(見 §2、§4),PacGen 的解法可大量借用。
- **版本 v2.5 與 3D exe [推定]**:目錄同時有 `PANZER2.EXE`(852KB,1998-01-13)與 `PG3DE250.exe`(773KB,2013 時間戳,疑 v2.5「3D 加速」版)。兩者 **import 幾乎相同**(都用 DDRAW + 相同 GDI 文字 API,見 §2),故兩者文字機制一致;`PG3DE250` 檔名中的 `250` 對應 v2.5。本輪以 `PANZER2.EXE` 為主分析,3D exe 的差異(是否走 Direct3D / Glide、是否更高解析)標**[未探索]**。
- **內建關卡編輯器 [已實測]**:`PANZER2.EXE` 內含 `Save Scenario File` / `Open Scenario File` / `Save Campaign File` 等字串,且目錄有 `USERSCEN/`,PG2 本身附帶劇本 / 戰役編輯功能。

## 2. 技術盤點(檔案結構 + 文字渲染機制實測)

### 2.1 檔案結構 [已實測]

| 檔案 / 目錄 | 內容 | 與中文化的關係 |
|---|---|---|
| `PANZER2.EXE` (852KB) | 主引擎(VC++/DirectDraw) | UI 對話框資源、GDI 繪字、語言 / 字型選擇邏輯都在此 |
| `PG3DE250.exe` (773KB) | 疑 v2.5 3D 版 | 文字機制同 PANZER2.EXE;細節未探索 |
| `ENGLISH.DLL` (134KB) | 「語言 DLL」 | `.rsrc` 僅 2 個 STRINGTABLE(約十餘條錯誤訊息);**非** UI 主字串來源 |
| `PANZER2.DAT` (12.5MB) | 具名索引封裝檔 | 內含 387 個 `.SHP` 圖 + **3 個點陣字型** + `EQP`/`TXT`/`PAL` |
| `EQUIP97.TXT` / `.EQP` | 裝備:名稱(TXT)+ 數值(EQP 二進位) | 單位名稱在 TXT(可直接改) |
| `GUI97.TXT` (7KB) | GUI / 指令 / 國名 / 勝負標籤 | **UI 純文字主來源之一**,可直接改 |
| `MISC.TXT` / `NAMES.TXT` | 地形 / 戰鬥標籤;指揮官名 | 純文字,可直接改 |
| `SCENARIO/*.TXT` (302 檔) | 各劇本的地名 / 座標表 | 地圖標籤,純文字 |
| `SCENARIO/*.SCN` `*.MAP` `*.CAM` | 劇本 / 地圖 / 戰役(二進位) | 劇本簡報散文位置**[未探索]** |
| `MSS32.DLL` `SMACKW32.DLL` | Miles 音效 / Smacker 影片 | 執行相依,不需翻譯 |
| `reg.exe` `MSRUN32.EXE` `msreg.ini` | 註冊 / autorun | `msreg.ini` 的 `MSREGR.EXE` 是選配「Free Stuff」註冊,非遊玩必要 |
| `PnzrGen2.pdf` `README.TXT` | 手冊 | 選配翻譯 |

`PANZER2.DAT` 封裝格式 **[已實測]**:header `<u32 count=395><u32 0x1a3f>`,接 395 筆**固定 17-byte 記錄**(13-byte 補零檔名 + 4-byte LE 資料 offset),資料段從 `~0x1a43` 起。已寫出可靠 parser 重現全 395 筆索引。社群工具 **PG2 Mods Clearing House / MODGEN** 可 unpack/repack 此 DAT(見 §6),不必自寫。

### 2.2 文字渲染機制(全案樞紐)——**雙管線** [已實測]

PG2 的文字分兩條獨立管線,證據來自 import table + 反組譯:

**管線 A:GDI 對話框 / 選單(視窗層,好處理)**
- `PANZER2.EXE` import GDI32 的 `CreateFontA`、`TextOutA`、`GetTextExtentPoint32A`、`SetTextColor`、`SetBkMode`;USER32 的 `DialogBoxParamA`、`CreateDialogParamA`、`LoadStringA`、`LoadAcceleratorsA`、`FindResourceA`、`LoadLibraryA`。
- 呼叫點盤點(掃 `.text` 的 `FF 15 <IAT>`):`CreateFontA`×1、`TextOutA`×1、`DialogBoxParamA`×**17**、`CreateDialogParamA`×2、`SetTextColor`/`SetBkMode` 各 14。
- **`PANZER2.EXE` 的 `.rsrc`(25KB)含 23 個 DIALOG + 2 個 ACCELERATOR + 1 ICON**。對話框(選項、存讀檔、連線、錯誤框)的文字在**這些 DIALOG template 裡**,由 Windows 對話框管理器以 template 指定的字型繪製。
- 唯一的 `CreateFontA` @ `0x467b04`:facename **"Arial"**、height `-0x10`(16px)、charset `0x10`。
- **意義**:此管線走 Windows GDI → **可用系統 CJK 字型 + 對話框 charset 換字型渲染中文**,是最省事的一條。

**管線 B:遊戲畫面內文字(DirectDraw surface 層,是主要工作量)**
- 遊戲主畫面(地圖標籤、單位資訊、畫面內選單、標題)不走 GDI,而是把**自訂點陣字型**blit 到 DirectDraw surface。
- `PANZER2.DAT` 內有 3 個點陣字:**`FONTPG.DAT`**(287KB)、**`FONTFRA.DAT`**(14KB)、**`FONTGRM.DAT`**(6KB)。
- **字型選擇邏輯 @ `0x43e42c` [已實測]**:依全域語言 ID `[0x4a44a0]` 分流 —— `==9`(LANG_ENGLISH)載 `fontpg`、`==0xC`(LANG_FRENCH)載 `fontfra`、else 載 `fontgrm`(德)。即英 / 法 / 德各有一套點陣字。
- **`FONTFRA.DAT` / `FONTGRM.DAT` 的格式與 Pacific General 的 `TFONT` 完全同族 [已實測]**:header 16 bytes(版本 `"1."`、glyph 數 256/128、glyph 高 **8**、maxidx 255)+ 0x10 起的 256×4 offset table + 每 glyph `[u32 width][width×8 bytes 點陣]`,**前景 pixel=0x00、背景=0xff**(與 PacGen 一致)。實際渲染 `'A'`/`'1'` 逐 row 印出可辨字形已確認理解正確。
- `FONTPG.DAT`(英文主字型)是**較大的變體**:header 版本 `"1.10"`,與 `.SHP` 同族的多幀格式,glyph 較大,尚未完整解碼(**[推定]** 為 SHP 式字圖表)。
- **意義**:8×8 點陣**物理上塞不下可讀中文**(PacGen 同款問題)。此管線要中文化,得走 PacGen 已實證的 **route C(不動畫布 + 拉高字高 + 2-byte hook + CJK atlas)**,見 §4。

**小結(樞紐結論)**:
> PG2 的 UI 文字 = **GDI 對話框(換字型即可)** + **DirectDraw 點陣字(需自建 CJK 字庫 + 2-byte hook,同 PacGen route C)** + **一堆純文字資料檔(直接改)**。三者各自獨立處理。點陣字管線與 PacGen 同族,是本專案能大量複用既有成果的關鍵。

## 3. 中文化標的與機制

| 標的 | 來源 | 渲染管線 | 改法 | 難度 |
|---|---|---|---|---|
| 指令 / 選單 / 國名 / 勝負 | `GUI97.TXT`(440 行) | B(畫面內) | 直接改文字 + CJK atlas | 低(文字)/ 中(字庫) |
| 地形 / 戰鬥標籤 | `MISC.TXT`(27 行) | B | 同上 | 低 |
| 單位名稱 | `EQUIP97.TXT`(586 行) | B | 同上;`.EQP` 數值不動 | 低 |
| 指揮官名 | `NAMES.TXT`(400 行) | B | 音譯或保留原文 | 低 |
| 劇本地圖標籤 | `SCENARIO/*.TXT`(302 檔 / 5613 行) | B | 地名多為專有名詞,擇要譯 | 中(量大) |
| 對話框 / 選單 UI | `PANZER2.EXE` `.rsrc`(23 DIALOG) | A(GDI) | 改 DIALOG template 文字 + charset/facename | 中 |
| 錯誤 / 系統訊息 | `ENGLISH.DLL` `.rsrc`(2 STRINGTABLE) | A | 改 STRINGTABLE(或另做語言 DLL) | 低 |
| 圖內烤字(標題 LOGO 等) | `PANZER2.DAT` 的 `.SHP` | 圖 | 需重繪 SHP(選配) | 高(選配) |
| 劇本簡報散文 | **[未探索]**(疑在 `.SCN`/`.CAM`/DAT) | ? | 先定位 | 待查 |

**本地化機制(可直接利用)[已實測]**:
- PG2 **原生支援 4 種語言**:反組譯 `0x4679d3` 起是一串 stricmp,把設定值比對 `"english"`/`"french"`/`"german"`/`"spanish"` → 設語言索引 0–3;另有 `"language"` 設定鍵與 `"english.dll"` 由 `LoadLibraryA` 載入。即**遊戲本來就是為在地化設計的**(歐洲四語)。
- **CHT 策略:寄生一個現成語言槽**,不必新增語言分支:
  - **選項 1(推薦)——寄生法 / 德語槽**:把語言設為對應 `FONTGRM.DAT`(或 `FONTFRA.DAT`)的槽,**用 PacGen 完全相同的 TFONT 工具鏈**把該槽字型換成 CJK atlas(拉高字高 + 2-byte hook)。因為 fra/grm 是**簡單 8×8 TFONT**,可直接複用 PacGen 的 `build_cjk_font.py` 與 route-C 手法。
  - **選項 2——英語槽**:改 `FONTPG.DAT`,但其 `"1.10"` 格式較複雜,得先解碼,工程較大。
- **設定值 `[0x4b4d20]` 從哪讀 [未探索]**:靜態映像中該 buffer 為空(runtime 才填),推測讀 INI 或登錄檔的 `language` 鍵。動手前需靜態續追 `0x4679d3` 上游(rulebook 62),確定寫入 CHT 對應值的位置。

## 4. 字型 / 編碼 / 解析度方案

### 4.1 解析度與可讀性 [已實測 / 推定]
- **內部解析度 640×480、8bpp 256 色**:`INSTALL.NFO` 記 `art width 640 / art height 480`;`PANZER2.DAT` 內含 `.PAL` 調色盤、全 `.SHP` 為 paletted 圖 → 確認 256 色 paletted DirectDraw。
- 8×8 點陣塞不下可讀中文(第一性事實:64 pixel 塞 10+ 筆畫糊成黑塊)。
- **建議與 PacGen 一致走 route C**:**不動畫布**,只把點陣字管線的**字高從 8 拉到 16**(16×16 CJK,640×480 下清晰可讀、排版衝擊最小),不必做 route A(拉高整個 DirectDraw 畫布)那套 present RE。3D exe 若確為更高解析,CJK 只會更清楚。

### 4.2 點陣字管線(管線 B)—— 沿用 PacGen route C [推定,方法已在 PacGen 實證]
1. **確認字高是 memory-read**:反組譯 PG2 的 drawGlyph,若字高讀自 font header(如 `[font+8]`)即可改檔生效(PacGen 如此)。**[未探索]**:PG2 drawGlyph 位址與字高來源尚未定位。
2. **CJK atlas 做成與原 drawGlyph 相容的 mini-TFONT**(header height=16 + offset table + `[width][px]` glyph,前景 0x00 / 背景 0xff,務必 match 原生字型的透明語意)。
3. **自訂 dense 2-byte 私有編碼**(非裸 Big5):`dense=(lead-LEAD0)*W+(trail-TRAIL0)`,hook 純算術無查表,塞得進小 code cave。資料檔字串由 glossary 重產,重編碼零成本。
4. **繪字迴圈 hook**:偵測 lead byte → 算 dense、call 原 drawGlyph、`+=2`;ASCII 走原路徑 `+=1`。無 code cave 就追加 PE 節(`.cjk`)。
5. **多繪字路徑各自 hook**:單行 label 與 word-wrap 簡報若走不同模組,需各加同款 hook(PacGen 經驗)。

### 4.3 對話框管線(管線 A)—— GDI 換字型 [推定]
- 改 `PANZER2.EXE` `.rsrc` 的 23 個 DIALOG template:譯文字 + 把字型設為 CJK facename + charset(DIALOGEX 可帶 `CHINESEBIG5=136` 或 `DEFAULT_CHARSET=1`)→ Windows/wine 以 CJK 字型渲染。
- 唯一 `CreateFontA("Arial",…)` @ `0x467b04`:若該處也需顯示中文,把 facename patch 成 CJK 字型 + charset。
- **wine 端**已知配方:prefix 內放 Noto Sans CJK TC + `FontSubstitutes`(見本 repo `WINE-FONT-SETUP.md`);Windows 端系統本有 CJK 字型。

### 4.4 編碼決策 [已實測支撐]
- **資料檔本身是 8-bit clean**:`GUI97/MISC/EQUIP97/SCENARIO/*.TXT` 現況全 ASCII(high-byte=0)、CRLF;但法 / 德版用高位元組(重音字)證明 **parser 容忍 8-bit codepage**。故資料檔放高位元組不會被 parser 拒。
- **管線 B 用 dense 2-byte 私有編碼**(渲染端 hook 解),資料檔字串轉此編碼。
- **管線 A(對話框)用 Big5**(或對應 CJK 字型 charset 的碼)交給 GDI。
- TechDoc 記各檔大小上限:`EQUIP97.TXT`/`GUI97.TXT` 64KB、`NAMES.TXT` 32KB、`SCENARIO*.TXT` 32KB;中文字元佔更多 byte,譯文需控管檔案大小。

## 5. 跨平台執行方案(wine / AppImage + 現代 Windows)

### 5.1 wine 可跑性 —— 本輪實測結果 [已實測]
以 wine 11 + 專屬 `WINEPREFIX`(置於 `$HOME`)+ Xvfb,對 `PANZER2.EXE` 做四種顯示設定實測:

| 設定 | 結果 |
|---|---|
| 直接啟動,Xvfb 1024×768×**24** | 主視窗建立,DirectDraw 嘗試切 640×480 全螢幕 → `NtUserChangeDisplaySettings … returned -2`(BADMODE)→ 彈 **"DirectDraw Init FAILED"** 錯誤框 |
| `explorer /desktop` 1024×768×24 / ×8 | 空白,無有效渲染 |
| **直接啟動,Xvfb 原生 640×480×8** | **成功到主選單!** 主視窗 640×480、**無 DirectDraw Init 失敗框**,截到 **PANZER GENERAL II 標題畫面 + 底部選單圖示列**(見 `evidence/wine-titlescreen-640x480x8.png`) |

**結論**:
- ✅ `PANZER2.EXE` 在 wine 11 下**可執行並抵達主選單**;**無 CD 檢查牆、無註冊牆**擋啟動(主 exe 內查無 "insert CD" 類字串;那條在 ENGLISH.DLL 屬 ClubSSI 連線用)。
- ✅ DirectDraw 初始化在**顯示模式相符時成功**(原生 640×480×8 免切模式)。
- ⚠️ **障礙 1 —— 全螢幕切模式**:當桌面尺寸 ≠ 640×480,DirectDraw 要切模式,plain Xvfb 無 RandR 切換能力 → 失敗。真實 X server、Xvfb+RandR、或比照 AG/PacGen 的**虛擬桌面 / 打包 prefix 配方**可解。
- ⚠️ **障礙 2 —— 256 色調色盤**:成功截圖的顏色錯亂(綠 / 紅 / 黑),是 **8-bit PseudoColor 調色盤未套到截圖** 的擷取假影,非遊戲故障(幾何與內容完全正確)。實機真桌面 / truecolor DirectDraw 路徑下顏色會正常;此與 AG/PacGen「256 色才能跑」同類議題,本 repo 既有解法(`pgs.dll` 類 shim + 深度處理)可借鏡。
- 卡關紀律:本輪對「DirectDraw + headless 顯示」議題已試 4 種設定並取得正向結果(抵達選單),未再往「調色盤全對 + 打包 prefix」深追(屬實作階段)。

### 5.2 Linux AppImage 打包思路 [推定,沿用本 repo 既有管線]
- 比照 PacGen/AG 的 AppImage:自帶配置好的 `WINEPREFIX`(含 CJK 字型 + FontSubstitutes + 顯示 / 調色盤 shim)+ 遊戲本體 + patch 後的 EXE / 字型 → AppImage 雙擊即跑。
- 需解掉 §5.1 兩個障礙:全螢幕改走**虛擬桌面**或視窗化;256 色調色盤處理沿用本 repo 手法。

### 5.3 現代 Windows 相容性 [推定]
- DirectDraw 在 Win10/11 仍受支援(系統 `ddraw.dll` 相容層),多數 SSI DirectDraw 老遊戲可跑,8bpp 256 色 exclusive fullscreen 偶有調色盤 / 相容模式問題,常需「相容性模式 + 停用顯示縮放」。
- Miles(`mss32.dll`)/ Smacker(`smackw32.dll`)已隨遊戲附帶,不缺 runtime(與 PG1 缺 `WING32.dll` 的情況不同 —— PG2 不用 WinG)。
- 啟動時有一個「Small Fonts / 96 DPI」提示對話框(EXE 內字串),非致命,可按過。
- 打包:比照本 repo Windows 7-Zip SFX(免裝 runtime、雙擊即跑)。

## 6. 里程碑 / 工作分解 + 風險 + 未解問題 + 參考

### 6.1 建議里程碑
1. **M0 建測試迴圈**:固定 wine + 640×480×8(或虛擬桌面)+ 正確調色盤,能穩定截到正常顏色的主選單 → 一切改動的驗證地基。
2. **M1 純文字資料譯**:`GUI97 / MISC / EQUIP97 / NAMES / SCENARIO*.TXT` 建 glossary + 譯文(先驗證 parser 吃高位元組 / dense 編碼)。
3. **M2 點陣字管線 RE**:定位 PG2 drawGlyph / drawString、字高來源、繪字迴圈 hook 點;決定寄生哪個語言槽(建議 fra/grm 的 8×8 TFONT 槽)。
4. **M3 CJK 字庫 + 2-byte hook**:複用 PacGen route-C 工具鏈,做 16×16 atlas + dense 編碼 + PE 節 hook;實機看畫面內中文清晰。
5. **M4 對話框 / STRINGTABLE**:改 EXE 23 DIALOG + ENGLISH.DLL STRINGTABLE + charset/facename。
6. **M5 打包**:Linux AppImage + Windows SFX,比照 PacGen/AG。
7. **M6(選配)**:圖內烤字 SHP 重繪、劇本簡報散文(先解 M-未探索)、3D exe。

### 6.2 風險
- **點陣字管線 RE 未做**:M2/M3 是主要不確定性;雖與 PacGen 同族,PG2 是不同 EXE,drawGlyph 位址 / 字高來源 / hook 點都要重新定位(方法可靠、結論要現做)。
- **`FONTPG.DAT` "1.10" 格式未解**:若被迫用英語槽才需解;建議繞開(用 fra/grm 槽)。

## 7. 實作階段 RE 攻堅結論(2026-07-17,已 PoC)

使用者決策已定:**目標 exe = `PANZER2.EXE`(2D)**、**寄生法語槽 + 開機直接進中文**、**地名全譯**、**指揮官名上網查證譯名**。以下為據此做的深度 RE,兩個技術閘門皆綠。位址以 ImageBase `0x400000`(DYNAMICBASE=False,恆載入)。

### 7.1 閘門 A:語言預設 = 單 byte EXE patch [已實測 + wine PoC]

PG2 有**兩套互不相干的語言機制**(先前 §3 只看到 INI 那套):
- **INI 路徑(死路)**:`langInit @0x46798e` 讀 INI `[language] type=` → stricmp → 寫索引到 `[0x4b4e28]`;但**該索引全 .text 零讀取,不驅動字型/資源**。改 INI 沒用。
- **真正的主開關 `[0x4a44a0]`**:字型選擇 `0x43e42c`、資源後綴 `0x43fbc2` 等 4 處都讀它。`.data` 初值 = `0x09`(英),**file offset `0xa32a0`**。唯二 writer 在 `setLangFromString @0x480748`,但該函式是**死碼**(全檔無分支/指標指向它)→ runtime 永不覆寫,恆保持初值。

> **做法:file offset `0xa32a0` 的 `09 00 00 00` → `0C 00 00 00`(改第一 byte 09→0C)**,即恆走法語槽(LANG_FRENCH=0xC)。
> 這一個值同時驅動:字型載 `fontfra.dat`、資料檔後綴變 `.fra`(`0x43fbc2`)、及兩處 API readers。

**wine PoC 已證**(`WINEDEBUG=+file`):patched 版開機改開 `GUI97.FRA/EQUIP97.FRA/MISC.FRA/NAMES.FRA`(baseline 開 `.TXT`),主選單正常起、無 crash。→ **「一進去就是中文」機制成立。**

含意 / 取捨:
- **翻譯後的資料檔命名為 `*.fra`**(`GUI97.fra`、`MISC.fra`、`EQUIP97.fra`、`NAMES.fra`、`SCENARIO/*.fra`),符合原生法語版慣例。
- 若想保留 `.txt` 檔名只借字型槽:另加小 patch 把後綴函式 `0x43fc20` 的 `==0xC→.fra` 分支(`je 0x43fbe5`)NOP 掉即可解耦。**兩案擇一,實作時定。**
- **不必動 `english.dll`**(它只有十來條錯誤字串,由 INI `dll=` 鍵獨立載入,與 `[0x4a44a0]` 無關);INI 維持 `dll=english.dll` 避免「Cannot Load Language .DLL」。
- 待釐清:patched 版 `EQUIP97` 同時開了 `.fra` 與 `.txt`(疑 .txt fallback 或雙段載入),影響「保留 .txt 檔名」取捨,實作階段驗。

### 7.2 閘門 B:FONTFRA 點陣字管線 route C —— **GO** [已實測]

| 函式 / 全域 | VA | file off | 說明 |
|---|---|---|---|
| drawGlyph | `0x41b033` | `0x1a433` | `(dest,x,y,font,ch,xlat)` 6-arg cdecl |
| glyphWidth | `0x41b013` | `0x1a413` | `(font,ch)` → 前進寬度 |
| drawStringCore | `0x43e612` | `0x3da12` | 逐 byte 主繪字迴圈,**12 caller 匯流** |
| 現行字型全域 | `[0x4d74c4]` | — | fontfra 載入後存此 |

- **字高 = memory-read `[font+8]`**(drawGlyph blit 列數 `0x41b0d7 mov edx,[esi+8]`;drawString 換行 `0x43e6ff`)。FONTFRA.DAT header:`ver "1."`、glyph 數 0x100、**height @off8 = 0x08**、offset table @0x10,與 PacGen TFONT 同族。→ **改 header off8 08→16 + 每 glyph 補到 16 列即生效,EXE 不動**(PacGen `font_rebuild.py` 複用)。
- **高位元組原生不畫**:繪字迴圈用 `movsx` + `cmp eax,0x20; jl`,0x80–0xFF 被當控制碼跳過 → **2-byte hook 是畫中文的必要條件,與原生零衝突**。
- **主 hook @ `0x43e699`(file `0x3da99`)**:以 `E9 rel32` 覆寫;迴圈狀態全 ebp-relative(`i=[ebp-0x10]`、pen x=`[ebp+8]`、y=`[ebp+0xc]`、xlat=`[ebp+0x10]`、str=`[ebp+0x14]`、dest=`[ebp+0x18]`),stub 無需存暫存器。lead byte→算 dense、`call 0x41b033`(font=atlas)、pen+=glyphWidth、`inc [ebp-0x10]`+回 back-edge 共 +2;ASCII 走原路徑。
- **多繪字路徑(各需同款 hook)**:① drawStringCore(主 UI,已定 hook)② `0x43e752`(word-wrap/clipped,briefing/清單;drawGlyph call @`0x43e9e1`/`0x43eaf9`)③ `drawStringSimple 0x41b1c6`(NUL 結尾,無直接 caller,實測用到再補)。量測寬度迴圈也要 2-byte 寬度感知(否則置中/斷行座標錯)。
- **空間**:`.text` 無足夠 cave + atlas ~140KB → **追加 PE 節 `.cjk`**(RVA `0x17f000`/VA `0x57f000`,NumSections 6→7)。base 固定 → 絕對立即數免 reloc,同 PacGen。
- **⚠ atlas 前景=0x00 / 背景=0xff** 要與 FONTFRA 一致(避免 PacGen 曾踩的白底/透明顛倒 bug:atlas 像素語意與 font 補列值須與原生字型一致)。

> route C 與 PacGen 幾乎一比一:字高 memory-read、標準 TFONT、乾淨 cdecl、單 hook 覆蓋主路徑、固定 base 可追加節。工具鏈(`build_atlas.py`/`font_rebuild.py`/`build_hooked_exe.py`)可大量複用。

### 7.5 POC 建置實測(2026-07-18):PG2 已在 wine 顯示中文 ✅

在 PG2 副本上把 atlas + hook + dense 編碼全串起來,**wine 實機劇本清單成功渲染 16×16「山地戰」**,透明背景 / 顏色正確、無白底 bug(證據 `evidence/pg2-cjk-scenario-list*.png`、`pg2-atlas-glyph-proof.png`)。**route C 在 PG2 落地,最高風險排除。**

- **崩潰單一根因 + 通解**:各繪字函式的**量測迴圈**用 `movsx` 讀字元 → 高位元組變負 → `glyphWidth(font, 負)` @`0x41b02b` page fault(所有崩潰同源,非 stub bug)。**解:hook glyphWidth 入口 `0x41b013`,把 ch clamp 成 byte(`and dword[esp+8],0xff`)**,一處修好所有量測迴圈。
- **drawGlyph `0x41b033` 全 EXE 僅 3 個 caller**:①drawStringCore(已 hook,涵蓋選單/清單/標題**絕大多數 UI**)②drawStringSimple `0x41b1c6`(movzx,單 byte 安全但不畫 CJK)③word-wrap `0x43e752`。→ 主 hook 覆蓋面比預期廣。
- **完整 patch recipe(原檔動 36 bytes + 追加 0x5a00 `.cjk` 節)**:

  | 項 | VA / file | orig → new |
  |---|---|---|
  | A 主 hook | `0x43e699`/`0x3da99` | `0fbf45f08b` → `e9 62091400`(jmp STUB1) |
  | B glyphWidth clamp | `0x41b013`/`0x1a413` | `558bec5356` → `e9 68411600`(jmp GWCLAMP) |
  | C word-wrap 防崩 | 10 處 `0x43e82f`…`0x43ea31` | 每處 `0f be`→`0f b6`(movsx→movzx) |
  | D `.cjk` 節 | header | NumSections 6→7、SizeOfImage→`0x185000`、RVA `0x17f000`/VA `0x57f000`、chars `0x60000020`;STUB1@+0、GWCLAMP@+0x180、atlas@+0x200 |
  | E 語言 byte | file `0xa32a0` | `09`→`0C`(法語槽用;見下方 pivot,POC 未套) |

  dense=`(lead-0x81)*94+(trail-0xA1)`,STUB1 只用 eax/ecx/edx、含 trail/count 雙守衛。

### 7.9 第一性原理根本解:`_pctype` 指標 repoint(2026-07-18,取代 5 個 classifier patch)

先前逐條 patch classifier 是打地鼠;第一性原理攻根確認**截斷/空白/(null) 一族的共同根源**是 CRT ctype 表 `_pctype @0x4ba538`:classifier 用 `movsx byte`(符號延伸)讀字元,**高位元組 0x80–0xFF → 負索引 → 讀表前 shadow → class 0 → 被當非可列印/終止符**。全 EXE 有 **~10 個 mask-`0x157` 的同族 classifier**(不只 5 個)——劇本/戰役清單走其中 5 個(已 patch),**狀態列與採購走的是沒補到的 sibling**(`0x43ff02`/`0x43ffc5` 採購家族等),這正是它們還壞的原因。

- **不能砸表**(Chesterton fence):負 shadow 區(`0x4ba442–0x4ba540`)是活字串資料(`melerror.txt`、`language` 關鍵字、版本字串…);`_pctype` 是共用 CRT 表、51 個使用點,直接填值會砸掉別的邏輯。
- **做法 = 指標 repoint**(單一 4-byte 資料 patch + 新 `.ctyp` 節):自造表 `[128 word 負 shadow=0x0100(_ALPHA)][256 word 複製原 _pctype[0..0xFF]]`,把 `0x4ba538` 指標改指自造表正 0 位。正索引 0..0xFF 與原表**逐 byte 相同** → ASCII ctype、CRT movzx 高位元組行為**完全不變**(blast radius 最小);負 shadow=_ALPHA → movsx 高位元組 `&0x157≠0` 保留、任何高位元組不再截斷;無 _DIGIT/_SPACE/_CNTRL 位 → `isdigit/isspace/iscntrl(高位元組)` 仍 false(對 CJK 正確)。
- **實測(移除全部 5 個 classifier patch + extend_titlefix,只加 repoint,0 fault)**:劇本清單、**戰役選單**、工具列選單(儲存/載入/離開)全中文完整;數字/日期/資料檔解析/word-wrap 簡報 0 回歸。→ **repoint 是 5-patch 的嚴格超集**,還修好狀態列與採購家族;附帶消掉 `extend_titlefix.py` 對 sibling `0x43d3d4` 硬編錯堆疊槽的潛在 bug。
- **狀態列 `(null)` 定性(控制變因,同「馬德里攻勢」Turn 1,證據 `ctypefix/sb_3way.png`)**:en 顯示 `Republican Turn 1/Weather: Fair/…Victory N Turns` 全有效;guard(5-patch)= `12/16/20 (null)`;repoint = `共和軍 回合 1/天氣:晴朗/12/16/20 回合數` 乾淨中文。→ **狀態列 `(null)` 是我方未補到的 ctype classifier 把名字截成空(§7.8「原版 cosmetic」判斷修正:是我方 bug),repoint 已修**。
